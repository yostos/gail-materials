= 推進の主体と範囲
include::../_attributes.adoc[]

[cols="1,1,4", options="header"]
|===
| 主語 | 範囲 | 正しい進め方

| 経営層 | 全社的な業務変革 | トップダウンで方向性を示す
| 部門リーダー | 自部門の業務 | 現場の課題から測定可能なユースケースを切り出す
|===

- 「誰が」「どの範囲を」動かす話かで正解が入れ替わる。設問の主語と範囲を先に読む。

== 全社変革はトップダウン

[cols="1,4", options="header"]
|===
| 推進手法 | 全社変革への適合性

| トップダウン戦略 | 経営目標、投資、優先ユースケース、ガバナンスを全社で統一できる
| ボトムアップ戦略 | 現場課題の発見には有効だが、全社最適と投資判断が弱くなる
| 自律的分散戦略 | 部門ごとの重複投資、セキュリティ差異、ガバナンス不統一が起きやすい
| 局所検証戦略 | PoC の学習には有効だが、全社デプロイと価値最大化につながりにくい
|===

- 設問に「全社的」「ビジネス価値の最大化」「業務変革」→ トップダウン。
- 全社規模の例: 顧客体験・店舗運営・需要予測・商品企画・サプライチェーン・問い合わせ対応の横断変革。
- 要るもの: 経営陣による明確な AI ビジョン、全社戦略との整合、優先ユースケースの選定、成果指標による測定。
- AI 施策を単独プロジェクトとして扱わず、企業全体の戦略に統合して投資領域を定める。

出典: link:https://services.google.com/fh/files/misc/ai_adoption_framework_whitepaper.pdf[AI Adoption Framework（ホワイトペーパー）]

== 部門ユースケースは現場起点

[cols="1,3", options="header"]
|===
| 検討項目 | 初期段階での位置づけ

| 業務課題とビジネス価値 | 最優先。ユースケースの妥当性、投資対効果、KPI を決める基準になる
| モデルの性能と推論コスト | 解くべき課題が決まった後の技術評価
| セキュリティとガバナンス | 利用データや接続方式が具体化してからの設計段階
| 研修と定着計画 | 対象ユースケースと利用者が決まった後の導入計画
|===

- 部門リーダーの役割は、測定可能なビジネス目標・現場の業務課題・ユーザー期待を結び付けること。
- 切り出す単位は「現場で使える」「効果を測れる」「業務プロセスに組み込める」。
- 全社的な刷新やモデル運用基盤の構築を選ぶのは職責の範囲外。
- 最初に決めるのは「どのモデルを使うか」ではなく「どの業務課題を解決し、どのビジネス価値を生むか」。
- 定義の粒度も価値側に寄せる。×「商品説明文を自動生成する」／○「商品登録作業の時間を削減し、公開までのリードタイムを短縮する」。
- 小売の成果指標の例: 売上向上、在庫最適化、サポート効率化、顧客満足度向上、解約率低下。

出典: link:https://docs.cloud.google.com/docs/ai-ml/generative-ai/evaluate-define-generative-ai-use-case[生成AIユースケースの評価と定義]、link:https://services.google.com/fh/files/misc/ai_adoption_framework_whitepaper.pdf[AI Adoption Framework（ホワイトペーパー）]

== 自動化適性の見極め

[cols="2,1,3", options="header"]
|===
| 業務の性質 | 自動化適性 | 理由

| 定型情報の抽出・要約 | 高い | 手順、入力、出力、評価基準を定義できる
| 主観的・創造的な提案 | 補助にとどめる | 人間によるレビューと判断が要る
| 新規事業戦略の決定 | 低い | 不確実性が高く、責任ある意思決定が必要
| コンプライアンスの最終承認 | 低い | 人間の監督・判断・承認を組み込むべき領域
|===

- 判断軸は、判断基準が文書化されているか・入出力の形式が安定しているか・反復回数が多いか。
- 生成AIの代表的な活用領域はテキスト生成・要約・情報抽出。いずれも人間の確認を前提にした支援として置く。
- 例: 商談メモから顧客課題・意思決定者・懸念点・次回提案の論点を抽出し、クライアント向けメッセージのドラフトを作る。最終的な内容と方針は担当者が確認する。
- 定型抽出・要約が最も適するのは、プロンプト設計・システム指示・構造化出力・評価データセットで入出力を制御できるため。
- 実装例: Vertex AI の `GenerateContent` API に文書を渡し、必要な項目を JSON 形式で抽出、または定められた観点で要約。
- 効果が出るのは、反復回数が多く人間が毎回同じ判断基準で処理している業務。時間短縮・品質の平準化・運用コスト削減。

外れる選択肢。

[cols="1,2", options="header"]
|===
| 選択肢 | 外れる理由

| 提案内容の完全自動決定 | 人間の判断と説明責任を欠く
| 既存業務システムの全面置換 | 記録・承認・監査・権限管理を含む。対話画面では代替できない
|===

== 作るか、つなぐか

[cols="1,1", options="header"]
|===
| 状況 | 選ぶもの

| 必要なデータが外部にすでに整備されている | API で連携する。精度・運用性・開発速度のすべてで勝る
| 独自クローラー・独自 NLP モデルを作る | 上記の条件下では外れる
|===

- Application Integration は、Google Cloud サービス・Salesforce などのビジネスアプリケーション・データベース・イベント駆動システムを連携し、データ変換とシステム間の処理自動化を実装するサービス。
- 例: 見込み客の企業規模・業種・利用技術を人手で調べている業務 → リード管理システムとサードパーティのセールスインテリジェンス SaaS を連携し、メールドメイン・会社名・URL をキーに企業プロフィールを自動補完。
- 設問に「既に整備された外部データがある」→ モデルを作る選択肢は外す。

出典: link:https://docs.cloud.google.com/application-integration/docs/overview[Application Integration の概要]

== 決定論が必要な処理はルールベース

[cols="1,3,2", options="header"]
|===
| 観点 | 生成AI（Gemini） | しきい値ルール

| 主な用途 | 自然言語理解、生成、要約、分類、推論 | 数値条件に基づく合否判定
| 判定の性質 | 確率的な生成・推論を含む | 同じ入力なら常に同じ結果
| 品質管理への適合性 | 判定根拠が固定条件ではないため中核エンジンには不向き | しきい値を明示でき、監査しやすい
|===

- 生成モデルの出力は `temperature`・`topP`・`topK` によって変化しうる。厳密な再現性と監査可能性が要求される中核の判定には向かない。
- 例: 「センサーの圧力値が規定のしきい値を超えたら不合格」→ `pressure > threshold` の固定ロジック。
- 実装手段: `if` 条件、決定表、ポリシールール、ワークフローの条件分岐。
- 合否判定エンジンに求められるもの: 監査性、再現性、説明責任。
- ファインチューニングは分類・要約・抽出型質問応答・チャットの性能向上には効くが、承認判定ロジックの代替にはならない。
