= プロンプト設計の技法
include::../_attributes.adoc[]

技法の前に、指示そのものを具体的にする。

[cols="1,2", options="header"]
|===
| 明記する要素 | 例

| 対象読者 | 経営層向けに
| 期待するトーン | 専門用語を避け
| 必須キーワード・観点 | TCO 削減、リスク低減、意思決定の迅速化を含めて
| 出力形式 | 3段落で提案書サマリーを作成する
|===

- 回答内容は正確でも、読み手に合っていない・専門用語が多い・観点が抜けている、という問題はここで直る。
- 追加開発もデータ基盤の構築も不要で即時に改善できるので、他の手段より先に見る。

[cols="1,5,3", options="header"]
|===
| 技法 | 何をするか | 設問での見抜き方

| ゼロショット | 例を示さず指示だけ与える | 例示なしで一般的なタスクを回す
| ワンショット | 例を1つだけ示す | 「例を1つ示して」
| フューショット | 入力と出力の例を数個示す | 「例をいくつか提示」「サンプル入力と出力」
| ロールプロンプティング | 役割・視点・口調を指定する | 「役柄」「トーン」「専門家として振る舞う」
| Chain-of-Thought | 複雑な判断を段階的な中間ステップに分解させる | 「推論手順を説明させる」「調査方針を順に組み立てる」
| ReAct | 推論に加えて、検索・API コール・ツール実行といった行動と観察結果を組み合わせる | 「考えて、動いて、結果を見てまた考える」
| プロンプトチェーン | 複数の処理を順に接続し、前段の出力を次段の入力として渡す | 「タスク分割」「前段の結果を次に渡す」「会話状態の引き継ぎ」
| プロンプトチューニング | モデルの重みは更新せず、学習可能なソフトプロンプト（プロンプト埋め込み）だけを最適化する軽量なチューニング手法 | 個々のタスクの解き方ではなく、追加学習の軽さが論点
|===

- Chain-of-Thought と ReAct の違いは行動の有無。前者は推論の分解のみ、後者はツールで外部の状態を観察しながら進む。
- エージェント（<<agents>>）の内部で使われるのは ReAct。
- プロンプトチューニングだけは書き方の技法ではなく追加学習の一種（PEFT）。プロンプト文言の作り込み（プロンプト最適化）とは別物。

== プロンプトチェーンと会話状態

- プロンプトチェーンの定義は「複数の処理を直列につなぎ、前段の出力を次段の入力に渡す」。会話状態の管理そのものを指す用語ではない。
- ただし状態を次段の入力として渡す形になるため、模擬試験では「対話の状態を引き継ぐ」要件の答えとして選ばれる。
- 引き継ぐ状態の例: 製品名、型番、症状、エラーコード、試行済みの手順。JSON などに整理して次のプロンプトに含める。
- Gemini API では、会話履歴や要約済みの状態をアプリ側で管理し、`contents` に必要な文脈を含める設計が基本。
- 効果は、単発の質問ではなく対話の流れを踏まえた解決策が返ること。

[cols="1,3", options="header"]
|===
| 技法 | 状態の引き継ぎに使えない理由

| フューショット | 出力形式の誘導であって、状態の引き継ぎではない
| RAG | 外部知識の検索であって、対話履歴の継承ではない
| Chain-of-Thought | 推論品質の向上であって、情報の保存・受け渡しではない
|===

出典: link:https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/chat/chat-prompts[マルチターンチャットの設計]、link:https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/prompts/break-down-prompts[プロンプトチェーンによる分割]

[#role-prompting]
== ロールプロンプティングとシステム指示

- 回答者の立場・専門性・話し方を固定する要件はこれ。
- 書き方の例: 「あなたはクラウドに精通したシニア講師です」「あなたはセキュリティアナリストです」。
- 制御するのは出力の観点・語調・説明粒度。

システムプロンプト。

[cols="1,5", options="header"]
|===
| 観点 | 内容

| 位置づけ | モデルがユーザー入力を処理する前に適用される上位の指示
| 指定するもの | 対象読者、役割、出力スタイルとトーン
| 効果 | 質問ごとに説明方針を書き直さずに、アシスタント全体の振る舞いを統一できる
| 実装 | Vertex AI の Gemini API では `systemInstruction`
|===

- 制約の例: 「IT に詳しくないユーザー向けに説明する」「専門用語を避ける」「必要な場合は日常的な例えで説明する」。

外れる選択肢。

[cols="1,4", options="header"]
|===
| 選択肢 | 外れる理由

| Top-P / Top-K | 表現のばらつきを抑えるだけ。対象読者向けの説明方針は定義できない
| プロンプトチェーン | 処理の分割。語り口の制御ではない
| RAG | 回答根拠の話。語り口の制御ではない
| フューショット | 役割を固定したいだけの要件には過剰
|===

出典: link:https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/prompts/system-instructions[システム指示の使い方]、link:https://ai.google.dev/gemini-api/docs/prompting-strategies[ペルソナとシステム指示]

== フューショットプロンプトの組み立て

[cols="1,5", options="header"]
|===
| 観点 | 内容

| 示すもの | 模範となる質問例と理想的な回答例を複数
| 伝わること | どのような形式・粒度・語調・構成で答えるべきか
| 例に織り込めるもの | 回答形式、見出し、注意事項、禁止表現、エスカレーション条件
| 書き方 | `<example>` と `<answer>` のような構造化タグで囲むと、入出力の対応関係を認識しやすい
|===

- 社内規定の形式に沿って安定的に回答させたいだけなら、再トレーニングよりこの手法が先。

出典: link:https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/prompts/few-shot-examples[フューショット例の使い方]、link:https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/prompts/structure-prompts[プロンプトの構造化]

[#chain-of-thought]
== Chain-of-Thought

- 複雑な判断を一度に答えさせず、一連の中間ステップに分解して推論の流れをたどらせる。
- Google Cloud のプロンプト設計では `Reasoning steps` として「ステップごとに推論を説明する」指示が扱われる。
- 効果は、原因候補をいきなり列挙させるより根本原因分析の思考プロセスを構造化できること。

障害切り分けの例。

[cols="1,5", options="header"]
|===
| 順 | 指示

| 1 | エラーコードから影響範囲と対象マイクロサービスを特定する
| 2 | 過去1時間以内のデプロイ履歴を評価する
| 3 | 変更がなければデータベースのコネクションプール枯渇や CPU スパイクを疑う
|===

出典: link:https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/prompts/explain-reasoning[推論の説明を促す指示]、link:https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/prompts/break-down-prompts[複雑なタスクの分解]
