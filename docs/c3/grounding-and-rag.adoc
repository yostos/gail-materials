[#grounding-and-rag]
= グラウンディングと RAG
include::../_attributes.adoc[]

[cols="1,3,4", options="header"]
|===
| 用語 | 位置づけ | 該当する要件

| グラウンディング | 出力を信頼できる情報源に結び付ける目的・制約 | 回答を自社の公式ドキュメントなど特定の情報源のみに制限する
| RAG | 情報を検索して生成に使うアーキテクチャ | 知識のカットオフを補うために外部を検索する
|===

- グラウンディングで得られるもの: ハルシネーションの抑制、回答根拠の提示、監査可能性の向上。
- RAG はモデルのパラメータを変えずに、検索・拡張・生成の流れで関連情報をプロンプトの文脈として渡す。
- 取り込み元は社内文書のほか Cloud Storage、Google Drive。

Vertex AI RAG Engine の処理順。

[cols="1,3,2", options="header"]
|===
| 段階 | 内容 | 使うもの

| コーパスへの取り込み | 外部ナレッジソースから文書を集める | Cloud Storage、Google Drive、社内文書
| チャンク化 | 検索単位に文書を分割する | 
| Embedding | チャンクをベクトルに変換する | Text Embeddings API
| インデックス化 | 検索できる形に索引を作る | Vector Search、ベクトル対応データベース
| 検索 | 質問に意味的に近いチャンクを取り出す | 
| 生成 | 取り出した内容をグラウンディング用コンテキストとして渡し、回答させる | 
|===

- 上表は典型的な RAG アーキテクチャ。Vertex AI Search をリトリーバルのバックエンドに据える構成も取れる。
- 運用上の要点は、知識の鮮度を検索対象の文書側で保てること。文書を更新し、取り込みとインデックス更新が済めば新しい内容が根拠になる。再学習は要らない。
- 「文書が頻繁に更新される」条件では、重みに埋め込むより検索対象として管理するほうが自然。毎回ファインチューニングし直す選択肢は外す。
- 「モデルが存在しない機能を答える」「回答を捏造する」は、生成能力の問題ではなく信頼できる外部ナレッジソースの不足として扱う。

グラウンディングの根拠は3種類。

[cols="1,2,2", options="header"]
|===
| データの出どころ | 中身 | Google Cloud の提供

| 自社データ | 社内文書、規程、FAQ、CRM | Vertex AI Search のデータストア、RAG API
| サードパーティデータ | 外部プロバイダから購入・契約するデータ | 取り込んでデータストア化
| ワールドデータ | 公開ウェブ上の情報 | Google 検索によるグラウンディング
|===

[cols="1,2", options="header"]
|===
| グラウンディングソース | 使う場面

| Google 検索 | 公開ウェブ上の最新情報を回答に反映する
| Vertex AI Searchのデータストア | 公式ドキュメントや社内文書を取り込んで根拠にする
| Vertex AI RAG Engine のコーパス | RAG パイプラインを自分で構成する
|===

- ソースの選択軸は、必要な情報が公開ウェブにあるか社内にあるか。
- 公開ウェブ側の実装: Gemini API の `GenerateContent` リクエストの `tools` に `google_search` を指定する。
- 公開ウェブが根拠になる情報の例: ニュース、企業発表、経済指標、相場。

外れる選択肢。

[cols="1,3", options="header"]
|===
| 選択肢 | 外れる理由

| プロンプトテンプレート | 質問形式や指示文を整えるだけ。モデルが知らない情報は補えない
| 生成後チェック | 回答の根拠確認や矛盾検出。生成前に最新情報を与える仕組みではない
| 再トレーニング | 更新頻度に対してコストが釣り合わない
|===
